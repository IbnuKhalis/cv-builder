## Temuan

### R1 — P1: sanitizer menghapus field valid pada model CV existing

Lokasi: `js/storage.js:232–288`.

Sanitizer memakai `current`, `school`, `name`, `technologies`, `issueDate`, dan `url`. Sementara `js/data.js`, form, preview, serta konverter teks existing memakai `isCurrent`, `institution`, `title`, `tech`, `year`, dan `credentialUrl`. Properti existing tersebut tidak dipertahankan dalam object hasil normalisasi.

Probe `mergeWithDefaults(sampleDataExperienced, defaultEmptyCV)` membuktikan enam field yang sebelumnya terisi menjadi tidak tersedia:

| Field | Sebelum | Sesudah |
| --- | --- | --- |
| `education[0].institution` | Institut Teknologi Bandung | Hilang |
| `projects[0].title` | Distributed Task Queue Library | Hilang |

Probe UI memuat sample, lalu reload: judul proyek dan tahun sertifikasi menjadi kosong. Normalisasi dijalankan saat startup, import, buka versi, dan restore; save berikutnya dapat menyimpan bentuk yang kehilangan field tersebut secara permanen.

Perbaikan: gunakan kontrak field yang benar-benar dipakai aplikasi; sanitasi tipe tanpa mengganti nama properti. Tambahkan tes round-trip seluruh field pada draft lama, kedua bahasa, import, pergantian versi, dan full backup.

### R2 — P1: tab yang sudah selesai autosave tetap dianggap memiliki edit tertunda

Lokasi: `js/app.js:2256–2277`, berkaitan dengan `js/app.js:2333–2354`.

Callback debounce tidak mengembalikan `saveDebounceTimer` menjadi `null`. Listener `storage` memakai timer tersebut sebagai penentu pending edit. Setelah pernah autosave, tab dapat terus masuk jalur partial merge walaupun sudah idle. Partial merge hanya melindungi/menyalin subset field berdasarkan fokus, bukan berdasarkan perubahan lokal yang belum tersimpan.

Reproduksi: tab B menyimpan `Initial Summary`; tab A menggantinya dengan `Latest Summary from A`. Tab B yang tetap berfokus pada ringkasan tidak menerima ringkasan terbaru. Ketika B mengedit target posisi, summary di storage kembali `Initial Summary`. Kehilangan data antar-tab masih terjadi.

Perbaikan: pisahkan status dirty dari ID timer, kosongkan timer setelah callback, dan gunakan revisi/konflik serta ID versi yang jelas. Uji bukan hanya dua tab yang baru dibuka, melainkan tab yang sudah pernah autosave serta edit beberapa bagian.

### R3 — P1: perpindahan versi tetap dilakukan saat flush gagal

Lokasi: `js/app.js:2168–2171`; pola sama pada pemanggilan flush di create/delete/reset/sample.

`flushAutoSave()` mengembalikan boolean, tetapi caller mengabaikannya. Fungsi juga membatalkan timer sebelum mengetahui save berhasil. State lalu diganti walaupun edit terakhir belum tersimpan.

Reproduksi: versi B memiliki edit `Version B UNSAVED`; simulasi kuota penuh pada koleksi, lalu buka versi A. Form pindah ke A, ID aktif menjadi A, tetapi draft masih B lama dan edit B terbaru hilang. Fix F1 melaporkan kegagalan, namun alur F2 tetap menghancurkan state yang belum dapat disimpan.

Perbaikan: jangan mengganti state/versi ketika flush gagal; pertahankan edit dan jalur backup. Tangani hasil mutasi storage berikutnya juga, termasuk hasil `saveCVToStorage()` pada perpindahan versi.

### R4 — P1: restore mengganti koleksi sebelum seluruh penulisan berhasil

Lokasi: `js/storage.js:686–690`.

Restore menulis koleksi dan ID aktif, kemudian memanggil `saveCVToStorage()` tanpa memeriksa hasilnya. Rollback pada save hanya menyasar draft; koleksi lama sudah diganti oleh restore. Fungsi tetap mengembalikan data sukses, sehingga UI bisa menampilkan “cadangan berhasil dipulihkan”.

Reproduksi: draft awal `Original Healthy CV`, backup `Restored CV`; simulasi kegagalan penulisan draft. Restore mengembalikan `Restored CV` tanpa throw, tetapi draft tetap `Original Healthy CV`, koleksi berisi `Restored CV`, status `save_error`, dan koleksi sehat sebelumnya sudah terganti.

Perbaikan: simpan snapshot seluruh key yang akan diubah, validasi sebelum menulis, propagasikan setiap kegagalan dan pulihkan semua key yang relevan. Jangan melaporkan berhasil saat hanya sebagian operasi selesai. Jika transaksi diperlukan, evaluasi penyimpanan yang mendukungnya.

### R5 — P1: backup dengan versi skema tidak dikenal diterima dan menimpa data sehat

Lokasi: `js/storage.js:656–677`.

Restore tidak memeriksa `schemaVersion`, tipe backup, struktur record CV secara ketat, atau keunikan ID. Object yang tidak dikenal dinormalisasi menjadi CV kosong lalu ditulis menggantikan koleksi lama.

Reproduksi: backup bertipe full backup dengan `schemaVersion: 999` dan record `data: {unknownFutureData: "content"}` diterima tanpa error. CV aktif menjadi kosong dan koleksi sehat diganti dengan ID `future`.

Perbaikan: whitelist versi skema yang didukung dan jalankan migrasi eksplisit; tolak versi masa depan tanpa mutasi storage. Validasi record serta ID unik sebelum overwrite. Hindari menganggap normalisasi menjadi empty default sebagai bukti backup valid.

### R6 — P1: entrypoint berversi masih mengimpor modul tanpa versi

Lokasi: `index.html:666` dan import `js/app.js:15–60`.

`?v=0.2.0` hanya diterapkan pada script utama dan CSS. Browser tetap meminta `/js/storage.js`, `/js/data.js`, `/js/ats-checker.js`, `/js/i18n.js`, serta kedua locale tanpa penanda release. Cache publik pada audit sebelumnya mengizinkan asset tersebut fresh selama empat jam.

Simulasi upgrade menggunakan `app.js?v=0.2.0` baru dan respons `storage.js` dari blob baseline lama membuktikan startup gagal: `The requested module './storage.js' does not provide an export named 'exportFullBackupJSON'`. Ini simulasi dependency lama yang tercache, bukan deployment yang sengaja dilakukan pada production.

Perbaikan: versioning harus mencakup seluruh dependency graph secara konsisten, atau URL release/hashing yang berubah untuk seluruh module; uji upgrade dengan cache lama. Mengubah cache HTML saja tidak membuat JavaScript dependency lama otomatis direvalidasi.

### R7 — P2: full backup tidak menyertakan edit yang masih menunggu debounce

Lokasi: `js/app.js:414–417` dan `js/storage.js:617–635`.

Handler backup langsung membaca koleksi/draft persisten tanpa flush atau snapshot state editor. Caller juga menampilkan toast sukses tanpa memeriksa boolean ekspor.

Reproduksi: nama tersimpan `Old Saved Name`; ubah menjadi `Latest Pending Name`, lalu klik full backup sebelum 350 ms. Baik versi maupun draft di berkas backup masih memuat `Old Saved Name`.

Perbaikan: pastikan full backup mencakup state terkini; bila flush gagal, pertahankan kemampuan backup edit yang belum tersimpan. Jangan menjadikan keberhasilan save sebagai satu-satunya syarat akses ke cadangan darurat. Periksa hasil ekspor sebelum menampilkan sukses.

### S1 — P1: edit gagal simpan hanya terlindungi pada percobaan switch pertama

Edit `UNSAVED B` hilang, padahal percobaan kedua dilakukan ketika storage sudah bisa digunakan kembali.

Perbaikan: pisahkan dirty state dari keberadaan timer. Dirty baru boleh dibersihkan setelah save benar-benar berhasil. Setiap aksi penggantian state harus mencoba menyimpan dirty state, termasuk setelah kegagalan autosave biasa atau setelah kegagalan flush pertama. Handler impor mengganti state, membersihkan dirty state, mengabaikan boolean `saveCVToStorage()`, lalu menampilkan pesan berhasil. Perbaikan failure path pada switch dan full restore belum mencakup jalur impor satu CV.
